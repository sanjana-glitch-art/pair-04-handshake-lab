2026-11-13  Kafka failure cases (Part 2) — full output: docs/evidence/kafka_failures.log
==============================================================================
$ ./scripts/kafka_failure_demos.sh       # runs inside the kind cluster

Case 1 — same event published twice
  [1a] the SAME envelope (event_id 472acdb1..., key 52:320) published twice
  [1b] a client retry: NEW event_id, same student+job key
  worker: "event already processed; skipping" -> outcome duplicate_skipped        (1a)
  worker: "application already stored; not inserting a duplicate" -> duplicate_skipped  (1b)
  [1] result: applications with _id=1506: 1; with student 52 + job 320: 1
  Fix/why it works: every envelope has an event_id; the worker records it in
  processed_events after the write and skips ids it has seen. The write itself
  uses unique keys (_id = application id, unique index student_id+job_id), so a
  retry with a new event_id cannot create a second row either.

Case 2 — worker killed during processing
  published a message with a 25 s pause before the database write (application 1508)
  worker p4-application-worker-...-gdjnn paused -> kubectl delete pod --grace-period=0 --force
  check right after the kill: application 1508: NOT stored
  stored 77 s after the kill:
  [2] result: applications with _id=1508: 1; with student 51 + job 320: 1
  Explanation: the event was NOT lost; it was reprocessed. enable.auto.commit=false and
  the runner commits the offset only after handle_message returns (database write done).
  The killed consumer never committed offset 4 on partition 1, so after the group
  rebalance (session timeout ~45 s) the other replica re-read it, paused 25 s, wrote it,
  then committed. Had the kill come after the write but before the commit, the
  redelivered copy would have been skipped by the case-1 idempotency check.

Case 3 — poison message
  published invalid JSON on key poison:1, then a valid message on the same key (same partition)
  worker: "message failed" attempt 1/3, 2/3, 3/3 (JSONDecodeError), backoff 0.5 s, 1 s
  worker: "moved to dead-letter topic" p4.application.created.dlq
  dead_letters: {topic p4.application.created, partition 0, offset 2, attempts 3, error JSONDecodeError ...}
  p4.application.created.dlq: {"original_topic": ..., "attempts": 3, "raw": "{\"event_id\": \"poison-..."}
  [3] valid message after the poison one: applications with _id=1509: 1
  Fix/why it works: bounded retries (WORKER_MAX_ATTEMPTS=3, exponential backoff), then
  the raw bytes and error go to <topic>.dlq and the dead_letters collection and the
  offset is committed, so the partition does not stall behind the bad message.
